Integrate Stage: Architecture Approaches

How should the code be structured? Three options, each with different trade-offs on modularity vs. simplicity.

Shared context: All approaches produce the same 4 artifacts (atom store, entity index, graph index, vector index). All use the same algorithms (entity resolution, relation detection). The difference is how the code is organized and how the sub-steps compose.

A

Monolithic Orchestrator

One integrate() function that runs all sub-steps sequentially. Each sub-step is a private helper in the same module.

engine/src/integrate/
  ├── index.ts           # integrate() — does everything
  ├── types.ts           # IntegrationResult, Entity, GraphEdge
  ├── prompts.ts         # LLM prompts for disambiguation
  └── errors.ts

Pros

  • Simple — one entry point, easy to follow
  • Fewer files, less indirection

Cons

  • index.ts will be 500+ lines
  • Hard to test sub-steps independently
  • Can't rerun just entity resolution
B

Sub-Step Modules (follows Extract pattern)

Each major sub-step gets its own file with a clear interface. index.ts orchestrates. Same pattern as the Extract stage.

engine/src/integrate/
  ├── index.ts               # integrate() — orchestrator only
  ├── entity-resolver.ts     # extractMentions() + clusterEntities() + disambiguate()
  ├── relation-detector.ts   # detectRelations() — reinforcement/contradiction/extension
  ├── graph-builder.ts       # buildGraph() — adjacency list from entities + relations
  ├── embedding-service.ts   # embedAtoms() — calls EmbeddingProvider, manages cache
  ├── types.ts               # All Integrate types
  ├── prompts.ts             # LLM prompts for entity disambiguation + relation classification
  └── errors.ts

engine/src/llm/
  ├── embedding-types.ts     # EmbeddingProvider interface
  └── openai-embedding.ts    # OpenAI adapter

Pros

  • Each file is testable independently
  • Follows existing codebase pattern
  • Can rerun individual steps
  • Files stay under ~200 lines each

Cons

  • More files to navigate
  • Types need to be well-defined at boundaries
C

Pipeline-of-Pipelines (over-engineered)

Each sub-step is a mini-pipeline with its own input/output types, own runner, and pluggable strategies. Entity resolution becomes its own configurable pipeline.

engine/src/integrate/
  ├── index.ts
  ├── entity-resolution/
  │   ├── index.ts
  │   ├── mention-extractor.ts
  │   ├── clusterer.ts
  │   ├── disambiguator.ts
  │   └── cross-domain-linker.ts
  ├── relation-detection/
  │   ├── index.ts
  │   ├── similarity-scorer.ts
  │   ├── classifier.ts
  │   └── confidence-updater.ts
  ├── graph/
  │   ├── index.ts
  │   ├── builder.ts
  │   └── serializer.ts
  ├── types.ts
  └── prompts.ts

Pros

  • Maximum separation of concerns
  • Each tiny piece is independently testable
  • Easy to swap strategies later

Cons

  • 14 files for a stage that might be ~800 lines total
  • Premature abstraction — we don't know which parts need to vary
  • Violates YAGNI hard

Shannon's recommendation: B. It follows the Extract stage's pattern exactly — Sam already knows how to navigate it. Each file has one clear job. A is too cramped, C is astronaut architecture for a problem we haven't fully explored yet. If a sub-module grows complex later, we can split it then — that's a refactor, not a rewrite.
