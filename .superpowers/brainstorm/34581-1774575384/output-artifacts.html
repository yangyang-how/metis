Integrate Stage Output Artifacts

What does the Integrate stage produce? Three stores need concrete formats.

Context: The design doc says "starting simple" — flat JSON files, in-memory adjacency list, ChromaDB for vectors. These are consumed by the Apply pipeline (not yet built). We want formats that are easy to inspect, debug, and iterate on.

1. Atom Store

CandidateAtoms become finalized Atoms. What changes?

CandidateAtom (Extract output)

{
  id: "ddia-ch5-sec2-3",
  frame: "causal",

  confidence: 0.85,
  source: { title, authors, chapterId, sectionId },
  domain: ["distributed systems"],
  flags: ["no_conditions"]
}

Atom (Integrate output)

{
  id: "ddia-ch5-sec2-3",
  frame: "causal",

  confidence: 0.90,        // ← boosted by reinforcement
  source: { ... },
  domain: ["distributed systems"],
  flags: ["no_conditions"],
  entityRefs: ["entity:replication-lag"],
  reinforcedBy: ["out-of-control-ch3-1"],
  contradictedBy: [],
  extendedBy: ["ddia-ch5-sec4-7"],
}

3. Graph Index

Adjacency list for traversal. Edges are typed.

Edge types:
  reinforces    — same claim, different source
  contradicts   — conflicting claims
  extends       — adds nuance/detail
  entity_link   — atoms share an entity
  cross_domain  — related entities across domains

Format: JSON adjacency list
  { "ddia-ch5-sec2-3": [
      { target: "out-of-control-ch3-1", type: "reinforces" },
      { target: "ddia-ch5-sec4-7", type: "extends" }
  ]}

4. Vector Index

Each atom embedded as a natural language sentence. Used for semantic retrieval in Apply.

Format options: ChromaDB (design doc's suggestion) vs. flat JSON embeddings file.
ChromaDB adds a dependency but gives us similarity search out of the box.
Flat JSON means we'd implement our own cosine similarity — simple but O(n) per query.

Recommendation: Start with flat JSON embeddings. 4K atoms × 1536-dim = ~24MB. Brute-force cosine similarity is fast enough at this scale. Add ChromaDB when we hit 50K+ atoms.
