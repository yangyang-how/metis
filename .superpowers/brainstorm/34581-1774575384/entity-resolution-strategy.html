Entity Resolution: How Aggressive?

When "feedback loop" appears in 3 different books across 3 domains, what should happen?

The scenario: "Feedback loop" appears in 福格行为模型 (behavioral triggers), Out of Control (emergent complex systems), and DDIA (replication lag). Same term, genuinely related concept, but different domain applications.

A

Conservative — Domain-Scoped Entities

Each domain gets its own entity node. "feedback loop (behavioral science)" and "feedback loop (distributed systems)" are separate entities with a related_to edge between them.

Pros

  • No false merges — domain nuance preserved
  • Retrieval stays precise within a domain
  • Simpler LLM calls (just "same concept in same domain?")

Cons

  • Cross-domain insights harder to surface
  • More entity nodes to manage
  • May miss genuine conceptual unity
B

Aggressive — Merge Across Domains

One entity node for "feedback loop" regardless of domain. All atoms from all books attach to it. Domain context lives in the atoms, not the entity.

Pros

  • Cross-domain connections are automatic
  • Fewer entities, simpler graph
  • Matches how experts think ("feedback loops are feedback loops")

Cons

  • False merges corrupt the graph (hard to undo)
  • Retrieval gets noisy — searching "feedback loop" returns everything
  • LLM must judge cross-domain equivalence (expensive, error-prone)
C

Layered — Merge Within Domain, Link Across

Entities are merged within the same domain. Across domains, a lightweight cross_domain_link edge connects related entities — not a merge, but a signal. The Apply pipeline decides whether to traverse it.

Pros

  • Best of both: precision within domain, serendipity across
  • Cross-domain links are cheap (no LLM, just embedding similarity)
  • Apply pipeline controls the blast radius per query

Cons

  • Two-tier resolution adds complexity
  • Must define "same domain" clearly
  • "Related across domains" threshold needs tuning

Shannon's recommendation: C. Conservative merging preserves domain precision. Cross-domain links are cheap and reversible — the Apply pipeline can choose to follow them or not based on query intent. False merges are expensive to undo; missed links are cheap to add later.
